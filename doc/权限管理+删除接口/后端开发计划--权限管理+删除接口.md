# VisionInfer V4.0 权限管理与删除接口设计方案

## 1. 设计目标

当前后端已经具备用户、模型、视频、任务和系统监控等模块，但各资源缺少删除能力，也缺少明确的权限控制边界。V4.0 版本建议补充“权限管理 + 删除接口”，使系统具备以下能力：

- 管理员可以维护全局资源。
- 普通操作员可以管理自己创建或上传的资源。
- 删除操作优先采用软删除，保留历史追溯能力。
- 接口方法使用标准 HTTP `DELETE`。
- 对正在运行或被引用的资源做保护，避免破坏任务链路。

## 2. 权限模型设计

### 2.1 权限字段

当前 `users.role` 字段属于用户自定义职位，例如“算法工程师”“操作员”“学生”等，不适合做权限判断。

建议新增独立权限字段：

```sql
ALTER TABLE users
ADD COLUMN permission_level TINYINT NOT NULL DEFAULT 0 COMMENT '权限等级：0=普通操作员，1=管理员',
ADD COLUMN account_status VARCHAR(32) NOT NULL DEFAULT 'active' COMMENT '账号状态：active/disabled';
```

权限定义：

| permission_level | 权限名称 | 说明 |
|---|---|---|
| `0` | operator | 普通操作员，可以删除自己提交的任务、自己上传的视频、自己上传的模型 |
| `1` | admin | 管理员，可以删除任意用户、任务、视频、模型 |

### 2.2 权限识别方式

短期建议 `DELETE` 接口通过请求头传递当前操作者：

```http
X-Operator-Username: chenwanyao
```

后端根据该用户名查询 `users.permission_level` 和 `users.account_status`。

对于 `POST /api/task/cancel`，为了保持 POST 请求风格统一，操作者放在 JSON Body 中：

```json
{
  "operator_username": "chenwanyao",
  "task_id": 12
}
```

基础规则：

- `DELETE` 接口请求头缺少 `X-Operator-Username`：返回 `401`。
- `POST /api/task/cancel` 请求体缺少 `operator_username`：返回 `400`。
- 用户不存在：返回 `401`。
- 用户 `account_status != active`：返回 `403`。
- 权限不足：返回 `403`。

### 2.3 后端建议新增 AuthService

建议新增 `service/auth/AuthService.h/.cpp`，统一做权限判断，避免每个 Controller 重复写鉴权逻辑。

建议能力：

```cpp
struct OperatorContext
{
    std::string username;
    int permission_level = 0;
    bool is_admin = false;
};

class AuthService
{
public:
    static bool getOperatorContext(const HttpRequest &req,
                                   OperatorContext &out_context,
                                   std::string &error_message);

    static bool canDeleteOwnedResource(const OperatorContext &context,
                                       const std::string &resource_owner);
};
```

判断逻辑：

- `permission_level == 1`：管理员，允许操作全局资源。
- `permission_level == 0`：普通操作员，只允许操作 `resource_owner == username` 的资源。

## 3. HTTP DELETE 支持

当前后端 CORS 允许方法为：

```http
Access-Control-Allow-Methods: GET, POST, OPTIONS
```

需要修改为：

```http
Access-Control-Allow-Methods: GET, POST, DELETE, OPTIONS
```

Router 继续使用当前的精确路由匹配模式，注册 `DELETE` 方法即可。

由于当前 Router 暂不支持 `/api/model/3` 这种路径参数，V4.0 第一阶段建议使用 Query 参数：

```text
DELETE /api/model?id=3
DELETE /api/video?id=5
DELETE /api/task?id=12
DELETE /api/user?username=testuser
```

这样既符合 HTTP 方法规范，也不需要大规模重构 Router。

## 4. 软删除策略

删除模型、视频、任务记录时，默认不直接物理删除数据库记录和磁盘文件，而是做软删除。

原因：

- 任务、视频、模型之间存在历史引用。
- 物理删除文件可能导致任务详情页、结果视频播放、统计数据出现断链。
- 毕设演示和压测记录需要保留可追溯性。

建议新增字段：

```sql
ALTER TABLE models
ADD COLUMN is_deleted TINYINT(1) NOT NULL DEFAULT 0,
ADD COLUMN deleted_at DATETIME NULL,
ADD COLUMN deleted_by VARCHAR(64) DEFAULT '';

ALTER TABLE videos
ADD COLUMN is_deleted TINYINT(1) NOT NULL DEFAULT 0,
ADD COLUMN deleted_at DATETIME NULL,
ADD COLUMN deleted_by VARCHAR(64) DEFAULT '';

ALTER TABLE tasks
ADD COLUMN is_deleted TINYINT(1) NOT NULL DEFAULT 0,
ADD COLUMN deleted_at DATETIME NULL,
ADD COLUMN deleted_by VARCHAR(64) DEFAULT '',
ADD COLUMN cancel_requested TINYINT(1) NOT NULL DEFAULT 0,
ADD COLUMN cancelled_at DATETIME NULL;
```

列表接口默认过滤：

```sql
WHERE is_deleted = 0
```

详情接口如果查到已删除资源，建议返回 `404`，除非后续专门做管理员回收站能力。

## 5. 模型删除接口

### 5.1 接口定义

```text
DELETE /api/model?id=3
```

请求头：

```http
X-Operator-Username: chenwanyao
```

成功响应：

```json
{
  "code": 200,
  "msg": "模型删除成功",
  "data": {
    "model_id": 3,
    "delete_mode": "soft_delete"
  }
}
```

### 5.2 权限规则

| 操作者 | 是否允许删除 |
|---|---|
| admin | 可以删除任意模型 |
| operator | 只能删除自己上传的模型 |

模型归属字段使用 `models.uploaded_by`。

### 5.3 删除限制

- 当前激活模型不允许直接删除。
- 模型不存在或已删除，返回 `404`。
- 普通操作员删除非自己上传的模型，返回 `403`。
- 模型被历史任务引用时，仍允许软删除，但不物理删除模型文件。
- V4.0 第一阶段不建议提供 `delete_file=true`，避免误删模型文件导致历史任务不可追溯。

### 5.4 后端处理流程

```text
1. 从请求头读取 X-Operator-Username。
2. AuthService 查询操作者权限。
3. 解析 Query 参数 id。
4. 查询模型记录。
5. 检查模型是否存在、是否已删除。
6. 检查权限：
   - admin 放行。
   - operator 需要 model.uploaded_by == operator.username。
7. 检查 is_active：
   - is_active = 1 时拒绝删除，提示先切换当前模型。
8. 更新模型：
   is_deleted = 1,
   deleted_at = NOW(),
   deleted_by = operator.username。
9. 返回删除成功。
```

## 6. 视频删除接口

### 6.1 接口定义

```text
DELETE /api/video?id=5
```

请求头：

```http
X-Operator-Username: chenwanyao
```

成功响应：

```json
{
  "code": 200,
  "msg": "视频删除成功",
  "data": {
    "video_id": 5,
    "delete_mode": "soft_delete"
  }
}
```

### 6.2 权限规则

| 操作者 | 是否允许删除 |
|---|---|
| admin | 可以删除任意视频 |
| operator | 只能删除自己上传的视频 |

视频归属字段使用 `videos.submitted_by`。

### 6.3 删除限制

- 视频不存在或已删除，返回 `404`。
- 普通操作员删除非自己上传的视频，返回 `403`。
- 如果视频存在 `PENDING`、`QUEUED`、`PROCESSING` 状态的任务引用，禁止删除。
- 如果视频已被历史任务引用：
  - operator 禁止删除，避免破坏自己的历史任务链路。
  - admin 可以软删除，但不物理删除视频文件。
- V4.0 第一阶段不物理删除 `storage/videos/input` 中的视频文件。

### 6.4 后端处理流程

```text
1. 从请求头读取 X-Operator-Username。
2. AuthService 查询操作者权限。
3. 解析 Query 参数 id。
4. 查询视频记录。
5. 检查视频是否存在、是否已删除。
6. 检查权限：
   - admin 放行。
   - operator 需要 video.submitted_by == operator.username。
7. 查询该视频关联任务。
8. 如果存在 PENDING/QUEUED/PROCESSING 任务，拒绝删除。
9. 如果存在历史任务引用且操作者不是 admin，拒绝删除。
10. 更新视频：
    is_deleted = 1,
    deleted_at = NOW(),
    deleted_by = operator.username。
11. 返回删除成功。
```

## 7. 任务删除接口

### 7.1 接口定义

```text
DELETE /api/task?id=12
```

请求头：

```http
X-Operator-Username: chenwanyao
```

成功响应：

```json
{
  "code": 200,
  "msg": "任务记录删除成功",
  "data": {
    "task_id": 12,
    "delete_mode": "soft_delete"
  }
}
```

### 7.2 权限规则

| 操作者 | 是否允许删除 |
|---|---|
| admin | 可以删除任意任务记录 |
| operator | 只能删除自己提交的任务记录 |

任务归属字段使用 `tasks.submitted_by`。

### 7.3 删除限制

- 任务不存在或已删除，返回 `404`。
- 普通操作员删除非自己提交的任务，返回 `403`。
- `PENDING`、`QUEUED`、`PROCESSING` 状态不允许直接删除，应先调用取消任务接口。
- `COMPLETED`、`FAILED_*`、`REJECTED_*` 状态允许删除。
- 删除任务记录默认不删除结果视频文件。

### 7.4 可删除状态

允许删除：

```text
COMPLETED
REJECTED_QUEUE_FULL
REJECTED_DISK_FULL
FAILED_INPUT_NOT_FOUND
FAILED_OUTPUT_DIR
FAILED_METADATA
FAILED_INFERENCE
FAILED_ENCODE
FAILED_OUTPUT_COPY
FAILED_RUNTIME
CANCELLED
```

不允许直接删除：

```text
PENDING
QUEUED
PROCESSING
```

### 7.5 后端处理流程

```text
1. 从请求头读取 X-Operator-Username。
2. AuthService 查询操作者权限。
3. 解析 Query 参数 id。
4. 查询任务记录。
5. 检查任务是否存在、是否已删除。
6. 检查权限：
   - admin 放行。
   - operator 需要 task.submitted_by == operator.username。
7. 检查任务状态：
   - PENDING/QUEUED/PROCESSING 拒绝删除，提示先取消任务。
   - 终态任务允许删除。
8. 更新任务：
   is_deleted = 1,
   deleted_at = NOW(),
   deleted_by = operator.username。
9. 返回删除成功。
```

## 8. 取消任务接口

另外建议补一个取消任务接口：

```text
POST /api/task/cancel
```

请求：

```json
{
  "operator_username": "chenwanyao",
  "task_id": 12
}
```

状态规则：

| 状态 | 是否可删除 | 是否可取消 |
|---|---|---|
| `PENDING` | 不建议 | 可以 |
| `QUEUED` | 不建议 | 可以 |
| `PROCESSING` | 不建议 | 可以真正取消 |
| `COMPLETED` | 可以 | 不需要 |
| `FAILED_*` | 可以 | 不需要 |
| `REJECTED_*` | 可以 | 不需要 |

数据库给 `tasks` 加：

```sql
is_deleted TINYINT(1) DEFAULT 0,
deleted_at DATETIME NULL,
deleted_by VARCHAR(64) DEFAULT '',
cancel_requested TINYINT(1) DEFAULT 0,
cancelled_at DATETIME NULL
```

## 9. 用户禁用接口

虽然接口可以命名为删除用户，但实际不建议物理删除用户记录，因为任务、视频、模型都保存了用户名作为历史归属。

### 9.1 接口定义

```text
DELETE /api/user?username=testuser
```

请求头：

```http
X-Operator-Username: admin
```

成功响应：

```json
{
  "code": 200,
  "msg": "用户已禁用",
  "data": {
    "username": "testuser",
    "account_status": "disabled"
  }
}
```

### 9.2 权限规则

- 只有 admin 可以禁用用户。
- operator 不允许禁用用户。
- admin 不允许禁用自己，避免误操作导致无法继续管理系统。

### 9.3 后端处理流程

```text
1. 从请求头读取 X-Operator-Username。
2. AuthService 查询操作者权限。
3. 检查操作者是否为 admin。
4. 解析 Query 参数 username。
5. 查询目标用户。
6. 如果目标用户不存在，返回 404。
7. 如果 operator_username == target_username，返回 400，禁止禁用自己。
8. 更新 users.account_status = 'disabled'。
9. 返回禁用成功。
```

登录接口需要同步修改：

```text
只有 account_status = active 的用户允许登录。
disabled 用户登录时返回 403。
```

## 10. 接口汇总

V4.0 建议新增接口：

```text
DELETE /api/model?id=模型ID
DELETE /api/video?id=视频ID
DELETE /api/task?id=任务ID
DELETE /api/user?username=用户名

POST /api/task/cancel
```

不新增：

```text
POST /api/system/cleanup
```

## 11. 状态码约定

| 状态码 | 含义 |
|---|---|
| `200` | 操作成功 |
| `400` | 参数错误或当前状态不允许操作 |
| `401` | 缺少操作者身份或操作者不存在 |
| `403` | 权限不足或账号被禁用 |
| `404` | 资源不存在或已删除 |
| `500` | 服务端处理失败 |

## 12. 推荐开发顺序

1. 数据库新增 `users.permission_level`、`users.account_status`。
2. 数据库新增 `models/videos/tasks` 的软删除字段。
3. 数据库新增 `tasks.cancel_requested`、`tasks.cancelled_at`。
4. 修改 `HttpParser::buildResponse` 的 CORS，允许 `DELETE`。
5. 新增 `AuthService`，统一读取 `X-Operator-Username` 或 Body 中的 `operator_username` 并判断权限。
6. 修改列表和详情 DAO，默认过滤 `is_deleted = 0`。
7. 实现 `DELETE /api/task`。
8. 实现 `POST /api/task/cancel`，并在视频处理流程加入取消检查点。
9. 实现 `DELETE /api/video`。
10. 实现 `DELETE /api/model`。
11. 实现 `DELETE /api/user`，实际执行账号禁用。

## 13. 关键设计结论

- 权限字段使用数字：`0=operator`，`1=admin`。
- `users.role` 保持为用户自定义职位，不参与权限判断。
- operator 可以删除自己上传的模型、视频，以及自己提交的任务记录。
- admin 可以删除全局资源。
- 删除接口统一使用 `DELETE /api/...`。
- 删除默认软删除，不物理删除文件。
- 运行中任务不能直接删除，必须通过 `POST /api/task/cancel` 取消。
